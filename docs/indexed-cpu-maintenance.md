# 首屏索引的真实 CPU 维护试验

这是[索引接口验证](read-index.md)之后单独声明并执行的一次正常场景。固定 Qwen3.5-9B 第三方 Q4_K_M、官方 llama.cpp、4线程CPU及非思考模式，保留上一轮模型、采样、症状提示、固定原版测试与独立契约。启用 `python_read_index_v1` 后，首屏会附索引，并增加通用读取建议；两项一起改变，不作单因素归因。

运行前固定[协议](../benchmarks/indexed_cpu_protocol.json)：单请求600秒、整场1800秒、服务2400秒，最多8份HTTP请求，单份65536字节、累计262144字节；1536输出token、40图步骤，零重试、零修复轮次。没有参考编辑计划，没有中途扩预算。任务JSON保留当时“已准备、未运行”的原始说明，以维持协议哈希；此后实际执行状态以本报告和日志为准。

## 实际结果

**在1800.035秒整场上限结束，未完成维护任务。** 保存4份模型回复、5条成功 `read_file` 结果；没有虚拟改动、导出补丁或验收。5份请求共预留143169字节，最后一份在途终止并继续占用额度，未耗尽次数或字节预算。

字面读取顺序为：

1. 生产文件和测试文件默认首屏，各1–100行。
2. 测试文件 `offset=100, limit=200`，即101–300行。
3. 生产文件 `offset=820, limit=100`，即821–920行，包含两个相关函数。
4. 生产文件 `offset=920, limit=100`，继续921–1020行。

前两个结果分别附2004/1377字节索引；生产索引列34项、省略1项，测试索引列15个直接声明、无省略。两者SHA与原始虚拟内容匹配，原始页保留。模型在看到这些结果后确实选择了覆盖相关函数的跨度，随后继续阅读；这只是观察，不能证明索引导致改善，更不是有效修复。

## 存储和验证范围

运行后核对实际状态目录为 **nfs4**，本机 `/tmp` 为ext4。[SQLite WAL不支持网络文件系统](https://sqlite.org/wal.html)。本次与历史记录只能支持实际发生的单机观察，不能证明这种持久化部署受支持，也不提供主机故障保证。未移动活跃数据库或改写原协议。下一项工程工作应先落实本机状态存储及启动预检，再开展新的模型试验。

只读审计通过图的 `get_state` 重建增量消息，没有调用模型或恢复运行。新通用[运行查看命令](run-inspection.md)在另一份固定源码上验证并读取了实时状态；当前模型继续使用启动前封存的 `7355b5a` 源码，不会因为本地新增命令而变化。最新90项回归属于接口及运行器，不能把它们算作这次模型任务成功。
