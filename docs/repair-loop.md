# 验收失败后继续修复

原有 `agent_lab.worker` 处理一份候选：编辑、落地、验收，失败则停止。
新增 `agent_lab.repair` 负责有次数上限的多个候选；没有隐式云端调用或无界重试。

```sh
python -m agent_lab.repair --repo /path/to/upstream \
  --task tasks/openhands-undo-model-repair.json --run-dir /path/to/local-state/repair-001
# 中断后使用相同任务、仓库与目录重新运行。
```

在 Linux 服务器准备环境的方法与
[OpenHands 维护协议](openhands-maintenance.md)相同：验收 Python3.13 环境放在
PATH 首位，运行器使用自己的环境。不要把两套依赖混装。

## 有界且可检查的轮次

- `max_repair_attempts` 默认 0，可显式设为 0–3；数值表示首次候选之后的额外轮次。
- 每轮从上一份失败候选的允许文件继续，有独立的 SQLite checkpoint、Git worktree、
  补丁、验收日志和 manifest。旧候选不会被后续编辑覆盖。
- 原来的 `max_graph_steps` 是每轮图步数预算，重启同一轮不重置；整个流程最多
  `(1 + max_repair_attempts) × max_graph_steps` 步。它不是 token 或费用预算。
- 每轮使用原任务相同的操作者验收命令。只有完成的、非超时、非信号终止的非零
  验收结果会进入反馈；导出范围错误、无补丁、模型服务错误等直接失败。
- 反馈包括失败命令编号、返回码、补丁和日志哈希，以及最多 8 KiB 的日志尾部。
  日志作为不可信输出放入提示词，不赋予其改变文件范围或验收配置的权限。
- 新候选重新运行全部验收；重启同一轮时，只在哈希仍匹配时复用已有结果。

顶层目录用锁串行化修复流程，各候选继续使用 worker / verifier 的锁。
失败记录与补丁核验后才被复用；日志或工作区变化会停止自动流程。反馈落盘后
即使父进程被 SIGKILL，也从已有失败记录推导下一轮，不靠内存计数器决定进度。
若旧验证仍持有候选锁，新的进程拒绝进入，待清理完成后可重试。

## 使用边界

这是顺序编辑—验收—修复流程，不是多 Agent 协作。`repair_plans` 仅用于明确标注的
脚本参考任务和故障验证；真实 `local-openai` 模式没有预先提供修复计划。
单候选入口与单候选模型 pilot 不应代替修复入口运行带额外轮次的任务。

模型只编辑虚拟文件；验收命令仍是操作者信任的代码，未提供恶意代码沙箱。
同一轮可能在“命令完成但结果未落盘”的崩溃边界重跑验收，不保证任意副作用恰好一次。
没有验证主机断电、监督进程被杀、进程组逃逸或提示词注入防护。

运行目录含源码、失败日志和模型上下文，应保持私人。公开证据只保留经检查的日志、
补丁与哈希；不能直接上传完整 checkpoint 或派生任务 manifest。

## 验证口径

HTTP fixture 检查真实传输与修复流程，返回明确编排的工具调用，不是神经模型。
真实 OpenHands 参考任务先生成一份不完整补丁，让独立权限验收实际失败；随后
使用固定纠正计划完成修复。正常和反馈边界 SIGKILL 的结果以公开证据报告为准。
这些实验检验流程与恢复，不证明模型修复成功率提升。


后续版本已增加[本机状态准入与共享归档](local-state.md)。写入口不再接受旧NFS状态路径；原始试验记录保留，只读检查与本机新控制的范围分别说明。
